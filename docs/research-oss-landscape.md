# Open-Source Synthetic Monitoring Landscape (2025–2026) — Competitive Research for SynthMK

Research conducted 2026-06-09 via web search + primary docs/repos. Each solution is scored on the six requested dimensions: (1) flow authoring, (2) scheduler/scaling, (3) secrets, (4) results/screenshots surfacing, (5) probe security model, (6) friendly vs. painful.

---

## 1. Checkmk Synthetic Monitoring (Robotmk v2) — the direct incumbent

The official feature SynthMK is the Raw-edition alternative to. **Commercial editions only (Pro/Ultimate), extra subscription on top; free tier = 3 tests / 15 keywords. Explicitly not compatible with Raw** — this is SynthMK's entire market opening. In Checkmk 2.5 the RCC tooling is being replaced by a Micromamba-based `csm` CLI, signaling Checkmk itself found RCC painful.

1. **Authoring**: Robot Framework `.robot` suites (keyword-driven DSL), usually with the Browser library (Playwright underneath) or Selenium. No recorder. Configured via a "Robotmk scheduler" bakery rule on the server: hierarchy of *parallel plan groups* → *sequential plans* → *suites*.
2. **Scheduler/scaling**: The scheduler runs as a permanent subprocess of the Checkmk agent on the test host. Each plan group has its own interval; plans within a group run sequentially (deliberately — to avoid desktop/GUI contention), groups run in parallel. The group interval must exceed the summed max runtimes of its plans — a manual capacity calculation users must do themselves. Per-attempt timeouts + Robot Framework re-execution (full or incremental retry of failed tests). RCC builds an isolated Python env per suite from `conda.yaml` (cached; rebuilt only on scheduler restart). Sizing guidance: 4–8+ cores, 8–16 GB RAM per test host; a forum user with 7 headless tests on 2 vCPU/4 GB got sporadic "Could not connect to the playwright process" errors and was told to double resources.
3. **Secrets**: "Secret environment variables" injected for robotframework-cryptolibrary so they don't appear in Robot logs — **but they land in plaintext in the agent config file on the test host**. Docs admit this is a security consideration.
4. **Results**: Three service types — `RMK Scheduler Status`, one `…Plan` service per plan, one `…Test` service per test — with the full Robot Framework HTML report and screenshots embedded in the test service in the Checkmk GUI. Keyword-level "KPI monitoring" (regex- or marker-discovered keywords become services with runtime thresholds). Built-in dashboards under Monitor > Synthetic Monitoring. Results ~500 KB–several MB per run, 14-day retention.
5. **Security**: Windows default = LocalSystem, optional "execute plan as specific user" — that combination caused **Werk #16434, a privilege-escalation to SYSTEM** when RCC env setup ran without a configured user. Linux scheduler runs as the agent user (typically root). Offline mode pins `ROBOCORP_HOME` paths to prevent code injection.
6. **Friendly/painful**: Friendly: plan/test/keyword as native Checkmk services, embedded HTML reports, central "managed robots" distribution, offline env catalogs. Painful (from forum threads): RCC env builds failing silently ("No data… none of the attempts produced any output"), envs only rebuilding on scheduler restart, SELinux vs. headless Chromium on RHEL9, bloated `rpaframework` deps, Robot Framework syntax churn, plaintext credentials, the licensing wall, and Robot Framework itself being a learning curve when all you want is "log in and check the dashboard loads."

## 2. Grafana Synthetic Monitoring + k6 browser

1. **Authoring**: k6 scripts in JS using the `k6/browser` module (its own async API — *not* Playwright; Chromium-only). Simple checks (HTTP/ping/DNS/TCP/traceroute/multi-HTTP) configured via UI/Terraform. Browser checks GA since May 2025. k6 itself is OSS (AGPLv3 — note copyleft), the **synthetic-monitoring-agent is open source but is a dumb executor for Grafana Cloud: scheduling, storage, alerting and the check registry live only in the cloud — there is no OSS backend**.
2. **Scheduler/scaling**: Agent ("private probe") polls the cloud API via token; checks are distributed across probes by the cloud scheduler. Capacity is expressed as resource budgets, not check counts: baseline 1 CPU/1 GiB for browser-capable probes, plus **~100m CPU / 256 MiB per browser-check-execution-per-minute** (vs 5m/2Mi for API checks) — i.e. a 4-core/8GB node ≈ 30–40 browser check-runs/min, ballpark. Docs say "monitor your probe for throttling/OOM."
3. **Secrets**: Best-in-class as of Aug 2025: centralized secrets store, envelope encryption (AES-GCM data keys wrapped by root key), referenced *by name* in scripts, **automatically masked in all check output**, fetched by private probes through a dedicated "secrets proxy", create/update restricted to admins via RBAC.
4. **Results**: Prometheus metrics + Loki logs into Grafana Cloud; prebuilt dashboards; browser checks capture Web Vitals. Screenshots/traces are comparatively weak vs Checkly.
5. **Security**: Probe is outbound-only (no inbound ports), single auth token, only reaches targets you configure; browser-capable probes ship as a separate `-browser` Docker image with Chromium included. Probe deactivates if token leaks/regenerated.
6. **Friendly/painful**: Friendly: resource-budget capacity tables, `-browser` image variant, secrets UX, outbound-only agent. Painful: k6 browser API ≠ Playwright (no codegen ecosystem, retrofit of existing PW tests required), Chromium-only, cloud lock-in for the control plane, AGPL considerations for embedding k6.

## 3. Uptime Kuma

1. **Authoring**: UI form per monitor. "Real Browser" monitor = single-URL Chromium load with screenshot. "Browser Engine" monitor delegates to a remote **browserless** instance. **No multi-step flows at all** — top-voted issues [#3056](https://github.com/louislam/uptime-kuma/issues/3056) and [#4804](https://github.com/louislam/uptime-kuma/issues/4804) beg for "paste a Playwright test" support, unimplemented for 3+ years.
2. **Scheduler/scaling**: Single Node.js process, per-monitor interval timers; scales fine for hundreds of HTTP checks, poorly for browsers (each Real Browser check spawns Chromium with no pooling/queueing).
3. **Secrets**: Plain fields in monitor config (basic auth, headers) stored in SQLite; no secret store, no masking.
4. **Results**: Status pages, uptime bars, response-time charts, screenshot of last Real Browser run, 90+ notification integrations.
5. **Security**: It pins an old internal Playwright (v1.39), causing hard breakage against modern browserless v2 (issue [#6216](https://github.com/louislam/uptime-kuma/issues/6216), 428 Precondition Required) — a cautionary tale about freezing a browser-driver version inside a monolith.
6. **Friendly/painful**: Friendly: the gold standard for 5-minute setup, gorgeous UI, huge community (60k+ stars). Painful: no flow chaining, no value extraction between steps, browser support is bolted on and version-brittle. **It proves demand for "simple self-hosted monitoring" but leaves the browser-flow niche wide open.**

## 4. Checkly (commercial, Playwright-native — the UX benchmark)

1. **Authoring**: Real Playwright Test specs (`.spec.ts`) used *unchanged* as monitors — "Monitoring as Code." The open-source **Checkly CLI** (constructs = TypeScript classes for Check/CheckGroup/AlertChannel; `testMatch` globs turn existing spec files into checks with default frequency/locations) and `npx checkly deploy` / `checkly test` for a test→deploy workflow. Recorder story = lean on Playwright's own codegen + VS Code extension rather than building one.
2. **Scheduler/scaling**: Cloud scheduler; for self-hosted **Private Locations** you run the `checkly/agent` container, which long-polls the cloud queue, executes, reports back. Stateless, horizontally scalable, ≥2 agents recommended for redundancy. Hard numbers: **`JOB_CONCURRENCY` default 1, max 10 per agent; ~1.5 GB RAM per browser check vs ~150 MB per API check**; browser checks min frequency 1 min, API 10 s.
3. **Secrets**: Account/group/check-scoped environment variables with an explicit variable-vs-secret distinction (secrets write-only, masked in logs/results), managed via UI or `checkly env` CLI.
4. **Results**: Full Playwright artifacts — traces, videos, screenshots, error logs — attached to each check run; trace viewer in the web UI. This is the artifact-surfacing benchmark.
5. **Security**: Agent is outbound-only with an API key per private location; scheduling/alerting/storage stay in their cloud (so the agent leaks no inbound surface but you don't own the data plane).
6. **Friendly/painful**: Friendly: zero-rewrite reuse of Playwright tests, code-first workflow with CI/CD diff+deploy, excellent docs. Painful: control plane is proprietary SaaS; private-location agent is useless without a paid account.

## 5. Prometheus blackbox_exporter (why it's not enough)

Authoring = YAML modules (http/tcp/icmp/dns/grpc) + target list in Prometheus scrape config. Stateless, massively scalable, trivially secure (no JS engine). But: no JavaScript execution, no DOM, no multi-step chaining, no value extraction between requests — an SPA that renders a blank page with HTTP 200 is "up." Regex-on-body and TLS-expiry checks are its ceiling. Standard advice (echoed even by OneUptime's own guides) is to pair it with real synthetic transaction monitoring. Its enduring lessons are operational: probe-side config is dumb/declarative, all intelligence lives in the scraper, and `probe_success`/`probe_duration_seconds` is a beautifully minimal result contract — very close in spirit to Checkmk local checks.

## 6. Elastic Synthetics (note the license split)

1. **Authoring**: `@elastic/synthetics` (npm, **MIT**) wraps Playwright with a `journey()`/`step()` API; also *lightweight monitors* defined in **YAML** (http/tcp/icmp) — a nice precedent for SynthMK's YAML-first approach. Plus **elastic/synthetics-recorder** (MIT, Electron+Playwright desktop app, still maintained — v1.4.15 Dec 2025): record clicks/inputs, add assertions, replay-test, export journey code.
2. **Scheduler/scaling**: "Projects" pushed via CLI to Kibana; execution on Elastic-hosted locations or **Private Locations = Elastic Agent + the synthetics integration** (containerized browser runner). Heartbeat browser checks are permanently beta and deprecated in favor of this.
3. **Secrets**: Params/env via `synthetics.config.ts`; cert paths only on private locations; Fleet-managed agent policy vars. Nothing as polished as Grafana's secret store.
4. **Results**: Rich Kibana Synthetics app — per-step screenshots, step durations, waterfalls, journey timelines. The per-step screenshot filmstrip is the visualization benchmark.
5. **Security/license**: The runner stack (Elastic Agent, Kibana app, Heartbeat) is **Elastic License 2.0 / SSPL-adjacent — not OSI open source**; only the npm library and recorder are MIT. Self-hosting the full experience requires the Elastic stack and its license terms.
6. **Friendly/painful**: Friendly: journey/step abstraction (named steps → per-step timing/screenshots), the recorder, YAML lightweight monitors. Painful: needs the whole Elastic stack; private location = full Fleet/Elastic Agent machinery; license ambiguity scares OSS purists.

## 7. sitespeed.io / browsertime

OSS web-*performance*-in-a-loop rather than up/down monitoring, but the closest long-lived precedent for "cron + browser + Grafana." Authoring: URL lists or Node "scripting" files for multi-step/login journeys (`commands.navigate`, `measure.start` …). Scheduling: you bring your own cron/CI; the `dashboard.sitespeed.io` repo is a docker-compose of sitespeed+Graphite+Grafana with ready dashboards. Secrets: `--browsertime.scriptInput.mySecret` CLI injection and config files that "hold secrets" — i.e., basically plaintext discipline. Results: HTML reports, screenshots-on-failure, videos, metrics to Graphite/InfluxDB. Lesson: their docker-compose "full stack in 5 minutes" quickstart is widely credited for adoption.

## 8. Newer / niche OSS Playwright-monitoring projects

- **basecamp/upright** (MIT, ~800★, v0.3.0, Rails) — self-hosted multi-site synthetic monitoring. HTTP/SMTP probes in **YAML**; browser probes as Ruby classes driving Playwright via a local browser server (`127.0.0.1:53333`). Solid Queue recurring jobs, `stagger_by_site` to spread load, Rails encrypted credentials for login secrets, video+logs+trace-viewer artifacts, Prometheus metrics on :9394, Kamal deploys to multiple geo VPSes. The most architecturally relevant new entrant.
- **workadventure/playwright-synthetic-monitoring** (MIT, tiny) — Docker image that loops standard `.spec.ts` Playwright tests every N seconds and exposes `/healthcheck` (200/500), `/metrics` (Prometheus), `/last-error` (last failed HTML report). Trivial but a great minimal-contract pattern: *any* uptime tool can consume it.
- **OneUptime** (Apache-2.0 full-stack platform) — synthetic monitors = user-supplied Playwright scripts executed on self-hosted probes, screenshots + logs + timings, viewport presets. **Two published advisories matter to SynthMK: GHSA-4j36-39gm-8vq8 (RCE via exposed Playwright browser object) and a sandbox-escape letting low-privileged project members run arbitrary commands on the probe.** Running user-authored JS on a probe is an RCE-by-design surface unless you sandbox hard.
- **Honorable mentions**: Gatus (YAML-declared health checks, no browser), selenwright (self-hosted Playwright browser cloud w/ VNC+video), playwright-live-recorder (in-browser recording bar inserting lines into the test file). Elastic's recorder remains the only polished standalone OSS recorder.

# Lessons for SynthMK

1. **Plan groups: sequential-within, parallel-across (Robotmk).** Robotmk's "parallel groups of sequential plans" is the right primitive for a runner node — headless flows parallelize, anything sharing a desktop/profile/account serializes. Adopt it in YAML (`group: payments` ⇒ serialized) and *compute* the Robotmk thing users must do by hand: warn at config-validate time if Σ(timeouts) in a group exceeds the group interval.

2. **Publish a capacity formula, enforce it with a worker pool (Grafana + Checkly).** Grafana's per-check-per-minute budget (~100m CPU/256Mi per browser run) and Checkly's hard numbers (1.5 GB/browser check, JOB_CONCURRENCY max 10) are the honest framing. For 50–100 checks/node: a fixed-size worker pool (start N = cores/2, cap ~6–8 on an 8-core/16GB appliance), a queue with per-check deadline, staggered start offsets (Upright's `stagger_by_site`), and a self-check service ("SynthMK Scheduler" à la `RMK Scheduler Status`) that goes WARN when queue latency or RAM says the node is oversubscribed. 100 checks @ 5-min interval ≈ 20 runs/min ≈ needs ~4–6 concurrent browser slots with 30–60s flows — feasible on one appliance, but only with pooling + shared persistent browser contexts (one Chromium, many contexts) instead of process-per-check (Uptime Kuma's mistake).

3. **Be Playwright-native, zero-rewrite (Checkly).** Checkly's killer feature is "your existing `.spec.ts` *is* the monitor." SynthMK's YAML should be the friendly layer, but accept a `type: playwright` step/flow that points at a raw spec file, so teams with existing tests onboard with zero translation — and YAML flows should compile to plain Playwright so users can graduate.

4. **Secrets: reference-by-name + masked output + root-only file (Grafana, anti-pattern: Robotmk).** Robotmk writes secrets plaintext into agent config — its single most criticized flaw. SynthMK: secrets live only on the runner node in a root-owned 0600 file (or systemd creds), YAML references `{{ secret.SHOP_PASSWORD }}` by name, values are injected as env at runtime and **regex-masked in every artifact** (logs, local-check output, HTML reports). Never let secret values transit the Checkmk server or git.

5. **Treat the runner as an RCE-by-design surface (OneUptime advisories, Werk #16434).** Both OneUptime (Playwright-object RCE + sandbox escape on the probe) and Checkmk (SYSTEM privilege escalation via RCC) shipped probe-side privilege bugs. SynthMK: dedicated unprivileged `synthmk` user, flows executed in a no-network-except-target sandbox where possible (bwrap/systemd hardening: NoNewPrivileges, ProtectSystem, PrivateTmp), and crucially **only the runner node decides what code runs** — config pushed from Checkmk should be declarative YAML, never arbitrary code, unless the operator explicitly enables a signed/allowlisted spec directory.

6. **Per-step granularity is the product (Elastic, Robotmk KPI).** Elastic's `journey/step` filmstrip and Robotmk's keyword-as-service show users want step-level timing, not just pass/fail. SynthMK YAML steps should each emit a name + duration; surface them as Checkmk metrics on the flow service (and optionally one local-check service per critical step with its own thresholds — Robotmk's pattern/marker discovery is a good model).

7. **Screenshot-on-failure + last-error HTML report, served from the node (workadventure, sitespeed.io, Checkly).** Checkmk local checks can't embed images, so copy the workadventure pattern: the runner appliance serves a tiny read-only HTTP endpoint (`/flows/<id>/last-failure/`) with the Playwright trace/screenshot/HTML report, and the Checkmk service output includes that URL. Auto-screenshot + trace capture *only on failure* keeps the 500KB–MB/run Robotmk artifact bloat away; add Robotmk-style 14-day retention/GC.

8. **Minimal result contract, blackbox-style.** `probe_success`/`probe_duration_seconds` and the workadventure `/healthcheck` prove the value of a tiny stable contract. SynthMK's local-check output should be exactly: state, flow duration, per-step durations as perfdata, failed-step name, artifact URL. Resist embedding logs in service output.

9. **Recorder UX: don't build one — integrate two existing ones (Checkly, Elastic).** Ship `synthmk record <url>` that (a) wraps `playwright codegen` and converts the generated actions into SynthMK YAML steps, and (b) document Elastic's MIT synthetics-recorder as the GUI path with a journey-code→YAML importer. A bespoke recorder is the trap; a *converter* is a weekend. (SynthMK note: our MV3 recorder already exists — keep it, but adopt the password-field→secret-step behavior.)

10. **Environment management is where Robotmk bleeds — keep the appliance image fat and static.** RCC env-build failures ("No data… blocked by settings", SELinux vs Chromium, rebuild-only-on-restart) dominate Robotmk forum pain, and Checkmk is replacing RCC with Micromamba in 2.5. SynthMK's appliance answer — pre-baked image/container with pinned Playwright + browsers, no per-flow env building — is genuinely the better model; lean into it. Add a `synthmk doctor` (deps, browser launch, SELinux/AppArmor, sandbox flags) because RHEL9+Chromium issues will hit your users too. And pin/upgrade Playwright deliberately with a compatibility test at startup — Uptime Kuma's frozen v1.39 broke the whole feature.

11. **Validate config server-side before deploy (blackbox/Gatus ethos + Robotmk anti-pattern).** Robotmk failures surface only at runtime on the agent. SynthMK should lint YAML (schema, selector sanity, secret references exist, group-interval math from lesson 1) at MKP-rule/bagging time and fail loudly *before* anything lands on the runner node.

12. **A 5-minute demo path decides adoption (Uptime Kuma, sitespeed.io).** Uptime Kuma's 60k stars come from `docker run` → working UI; sitespeed.io's adoption came from the one-command compose dashboard stack. SynthMK needs: one `docker run`/VM image for the runner node + one MKP install + one example flow (`example.com` title check) that turns green in Checkmk inside 5 minutes, no Robot Framework, no env builds, no subscription wall — that contrast with commercial Robotmk *is* the pitch.
